# REST 실무 용어집

REST 통신에서 자주 쓰이는 필수 개념만 설명형 문제 카드처럼 정리한다.

형식:
- 위 줄: 설명
- 아래 줄: 실제로 많이 쓰는 명칭
- 그 아래 줄: 짧은 예문

## HTTP 기본

클라이언트가 서버에 보내는 요청 전체.
요청[Request]
예: 로그인 요청[Request]에는 보통 헤더와 바디가 함께 들어간다.

서버가 클라이언트에게 돌려주는 응답 전체.
응답[Response]
예: 성공 시 응답[Response] 바디에 사용자 정보를 내려준다.

요청이나 응답의 부가 정보를 담는 메타데이터 영역.
헤더[Header]
예: `Authorization`은 대표적인 요청 헤더[Header]다.

실제 데이터 본문을 담는 영역.
바디[Body]
예: POST 요청의 바디[Body]에는 JSON 데이터를 넣는다.

응답 결과를 숫자로 표현하는 규약.
상태 코드[Status Code]
예: 정상 조회면 `200`, 생성 성공이면 `201`을 쓴다.

서버 자원을 식별하는 주소.
엔드포인트[Endpoint]
예: 사용자 목록 엔드포인트[Endpoint]는 `/users`일 수 있다.

## HTTP 메서드

데이터를 조회할 때 쓰는 메서드.
조회[GET]
예: 사용자 목록 조회[GET]는 보통 `/users`로 요청한다.

새 데이터를 만들 때 쓰는 메서드.
생성[POST]
예: 회원 가입 생성[POST] 요청은 `/users`로 보낼 수 있다.

기존 데이터를 전체 수정할 때 자주 쓰는 메서드.
수정[PUT]
예: 프로필 전체 수정[PUT]은 전체 필드를 보내는 편이다.

기존 데이터를 일부 수정할 때 자주 쓰는 메서드.
부분 수정[PATCH]
예: 닉네임만 바꿀 때는 부분 수정[PATCH]가 자연스럽다.

데이터를 삭제할 때 쓰는 메서드.
삭제[DELETE]
예: 계정 삭제[DELETE] 요청은 `/users/1`처럼 보낼 수 있다.

## 자주 보는 상태 코드

요청이 정상적으로 처리되었음을 뜻하는 코드.
성공[200 OK]
예: 목록 조회 성공이면 `200 OK`를 반환한다.

새 리소스가 생성되었음을 뜻하는 코드.
생성 완료[201 Created]
예: 게시글 작성 성공 후 `201 Created`를 내려준다.

잘못된 요청 형식이나 유효성 오류를 뜻하는 코드.
잘못된 요청[400 Bad Request]
예: 필수 값이 빠지면 `400 Bad Request`를 반환한다.

인증 정보가 없거나 잘못된 상태를 뜻하는 코드.
인증 실패[401 Unauthorized]
예: 토큰이 없으면 `401 Unauthorized`를 내려준다.

권한은 있지만 해당 작업이 허용되지 않음을 뜻하는 코드.
권한 없음[403 Forbidden]
예: 일반 유저가 관리자 API를 호출하면 `403 Forbidden`이다.

요청한 자원이 존재하지 않음을 뜻하는 코드.
찾을 수 없음[404 Not Found]
예: 없는 게시글 ID면 `404 Not Found`를 반환한다.

서버 내부 오류를 뜻하는 코드.
서버 오류[500 Internal Server Error]
예: 처리 중 예외가 나면 `500 Internal Server Error`가 날 수 있다.

## 인증 / 세션 / 토큰

브라우저에 저장되고 요청마다 자동으로 전송될 수 있는 작은 데이터 조각.
쿠키[Cookie]
예: 세션 기반 로그인에서는 쿠키[Cookie]에 세션 식별자를 담는다.

서버가 사용자 로그인 상태를 저장해 두는 방식.
세션[Session]
예: 서버는 세션[Session] 저장소에서 로그인 상태를 확인한다.

서버가 상태를 저장하지 않고, 클라이언트가 토큰을 보관하는 방식.
토큰 인증[Token Authentication]
예: 모바일 앱은 토큰 인증[Token Authentication]을 많이 쓴다.

JSON 형태로 서명된 토큰을 이용하는 인증 방식.
제이더블유티[JWT]
예: 로그인 성공 후 JWT를 발급해서 API 호출에 사용한다.

인증 정보를 요청 헤더에 넣어 보내는 방식.
베어러 토큰[Bearer Token]
예: `Authorization: Bearer <token>` 형식으로 보낸다.

## CORS / 브라우저 보안

브라우저가 다른 출처 간 요청을 제한하는 보안 정책.
동일 출처 정책[Same-Origin Policy]
예: 포트가 다르면 동일 출처 정책[Same-Origin Policy]에 걸릴 수 있다.

다른 출처 요청을 허용할지 정하는 브라우저 보안 규칙.
교차 출처 리소스 공유[CORS]
예: 프론트와 API 서버 도메인이 다르면 CORS 설정이 필요하다.

본 요청 전에 브라우저가 미리 보내는 사전 확인 요청.
프리플라이트 요청[Preflight Request]
예: `OPTIONS` 메서드로 프리플라이트 요청[Preflight Request]이 먼저 간다.

서버가 어떤 출처를 허용하는지 알려주는 응답 헤더.
출처 허용 헤더[Access-Control-Allow-Origin]
예: 개발 환경에서는 `http://localhost:3000`만 허용할 수 있다.

## 실무 패턴

클라이언트가 JSON을 보내고 서버가 JSON으로 응답하는 가장 흔한 패턴.
제이슨 API 패턴[JSON API Pattern]
예: `Content-Type: application/json`을 헤더에 넣는다.

로그인 후 토큰을 받아 이후 요청 헤더에 넣는 흐름.
토큰 로그인 플로우[Token Login Flow]
예: 로그인 성공 후 받은 토큰으로 `/me` API를 호출한다.

로그인 후 쿠키를 저장하고 이후 요청에서 자동 인증하는 흐름.
쿠키 세션 플로우[Cookie Session Flow]
예: 브라우저는 저장된 쿠키를 다음 요청에 자동으로 붙인다.

페이지 목록을 여러 조각으로 나눠서 조회하는 패턴.
페이지네이션[Pagination]
예: `/posts?page=2&limit=20`처럼 페이지네이션을 건다.

같은 요청을 여러 번 보내도 결과가 같아야 하는 성질.
멱등성[Idempotency]
예: 같은 삭제 요청을 두 번 보내도 최종 상태는 같아야 한다.
